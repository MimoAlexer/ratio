## Product decision

Open the app after four days away. Your Luma project’s issue “Rebuild stale backlinks” is still in progress. Home shows the next test you left yourself, the Markdown note explaining link resolution and the linked pull request. Beside it, one of your repositories has an open critical dependency alert. You can resume the test or start a fix without reconstructing context from three tools. On Friday, Release Review shows what actually shipped and which scope changes explain the remaining work.

Build this as a private, keyboard-first SaaS for one developer and one private workspace per account. It should serve a weekend developer with one project, an indie developer maintaining several apps and a freelancer keeping client projects separate. Recruit across all three. Organize the product around their shared task of resuming unfinished software work. Use one project as the onboarding unit, and give multi-project users a portfolio view.

| Decision | Basis |
|---|---|
| Tracker first. Work in progress and critical security issues on Home. A release chart showing what shipped and what changed. Personal adaptations of the five visual references. | Owner’s choices. |
| GitHub in the first release. Later, connect an existing AI assistant through MCP, followed by AI inside the app. | Owner’s requested sequence. |
| Practically all implementation in Rust. Use the most appropriate configuration format for each job. Fast web app on Railway. | Owner’s technical constraints. |
| Free, Plus at 5 monthly and Max between 10 and 20 monthly. | Owner’s price structure. |
| USD 0 / 5 / 15 per account, one owner, web first, first release in English. Private projects, manual checkpoints, read-only GitHub, Markdown transfer, explicit release publishing and a near-all-Rust runtime. | Recommended defaults the owner delegated. Hours, quotas, performance and conversion figures below are planning targets. |

Linear already has linked documents, cycles and issue analytics. Its listed Free tier includes 250 issues and Business includes Insights. Obsidian stores ordinary Markdown in folders and can show the local links around a note. A reason to switch is seeing the next experiment, the decision behind it and what reached a release from the same issue. Test that benefit against each pilot’s actual tools. [Linear documents](https://linear.app/docs/documents) · [Linear pricing](https://linear.app/pricing) · [Obsidian storage](https://obsidian.md/help/data-storage) · [Obsidian graph](https://obsidian.md/help/plugins/graph)

Two other sensible starting points were a vault-centered app, which makes concurrent file editing and conflict recovery early commitments, and a security-centered app, which makes repository coverage its main promise. The owner picked the tracker. GitHub supplies security context and Markdown keeps the work portable.

## Daily use

| Surface | What a developer can do |
|---|---|
| Home | Resume the latest meaningful work, review other in-progress issues across projects, and act on critical security findings. Show an explicit project name on every cross-project row. |
| Project | Switch between a compact list and board. Create an issue with a title, status, priority, labels, optional release, description and blocker. Filter, group, archive, undo a status change and search by title or issue key. Dragging and a keyboard-accessible status menu perform the same operation. |
| Issue | Keep a next action, source paragraph, related pull requests, release membership and change history together. A blocker is a relationship, so an item can be both in progress and blocked. |
| Notes | Write Markdown, link issues and notes with autocomplete, follow backlinks, or select a paragraph and create a linked issue. The new issue opens the source paragraph. If the anchor disappears, offer the note and retained excerpt from the user's own content. |
| Releases | Name a release, add or remove issues, review the manifest, then publish it with a date. Distinguish completed work awaiting release from items explicitly shipped. |
| Review | Select a release and week. Inspect shipped items, scope movement and work carried forward. Every chart mark opens the underlying issues or events. |
| Settings | Connect repositories, see permissions and last successful check, select timezone, export a project, manage subscription and delete the account. |

**Home ordering.** The developer can explicitly save a checkpoint on an issue. In the selected project, show the latest checkpoint on an open issue first, then the last in-progress issue they edited, then a prompt to choose one. All-project Home uses the freshest eligible checkpoint across projects and lists other active work below it. Finished, archived and deleted work drops out. A webhook, passive page view or reopened browser tab never steals the resume slot. Visible resume and alert records must both pass workspace filters. A new critical alert stays visible beside this selection. On a phone, place a one-line critical count and coverage above the resume card, followed by actionable alert rows.

**First five minutes.** Sign in, create or import one project, add one note explaining a real decision, turn a sentence into an issue and save a next step. GitHub connection is optional and independently removable. A demo project uses clearly labeled sample data and stays out of real charts. A blank workspace has a direct “Create my first issue” action. An empty security panel explains how to connect a repository or flag an issue manually.

**Interaction design.** Give current work and critical security alerts a shared, compact Home header. Use a continuous plotting surface, aligned list columns and a readable Markdown editor. Use Instrument Sans for interface text and IBM Plex Mono for keys, dates and axes; reserve the warm accent for the current date and urgent items. Support light/dark themes, reduced motion and narrow layouts. Start with Ctrl/Cmd+K for search and commands, C for creating an issue and a shortcuts dialog. Suppress letter shortcuts inside editors. Focus returns to the originating row when a panel closes. Confirm saved checkpoints, failed requests and stale data in text.

## GitHub and critical issues

Start with a read-only GitHub App installed on selected repositories. Each connected repository maps to one active project in a workspace. A project may have several repositories. Default new fixes to that project. On an explicit remap, move coverage and future alert attribution, preserve existing issue links and keep the workspace/repository/alert identity stable. Show linked PR number, title and state on an issue. Link by a pasted PR URL or an explicit tracker key in the PR title/body. Surface ambiguous matches for manual confirmation. A merged PR is evidence about code, while the developer controls issue completion and release publication. First import only referenced PR metadata. Give unconnected users a private manual security flag with a severity and next action.

Coverage follows supported dependencies on the default branch of repositories with GitHub dependency alerts enabled. Describe these as dependency alerts from GitHub, alongside the user’s own reports; unconnected services have unknown coverage. Use the repository Dependabot alerts endpoint with the read permission for Dependabot alerts and request read-only Pull requests for PR context. Keep metadata minimal. A connected source may be public or private. A public repository’s association with an advisory can still be private. Check the signed-in owner's effective alert access with a GitHub App user token. Verify that the user can bind the installation to the workspace. Store installation credentials separately from account sign-in. [Dependabot API](https://docs.github.com/en/rest/dependabot/alerts#list-dependabot-alerts-for-a-repository) · [Installation verification](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/about-the-setup-url) · [Alert visibility](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/configure-dependabot-alerts)

Show open upstream alerts whose reported severity is critical, and manually flagged critical items with a distinct origin label. Each imported row includes repo, package, affected manifest, optional patched version, GitHub link and last successful check. “Start fix” creates or opens exactly one private work item for that finding. For an imported finding, the linked row resolves sensitive details from the source on read. A user can name their own work item. Completing the local task keeps an upstream-open alert visible. A fixed or dismissed alert leaves the active panel and a reopened alert points to the existing fix record. Manual reports are closed locally.

Seed by paging through the selected repositories on connection. Process signed GitHub webhook deliveries through a deduplicated job queue. Re-read current source state for changed IDs, reconcile all accessible repos hourly with jitter and backoff, and offer rate-limited manual refresh. Track check time and coverage per repo. Only advance the cursor or record a confirmed zero after a complete successful sweep. On partial failure, show e.g. “0 critical in 2 checked repositories · 1 unavailable.” Mark a repo stale after two missed sweeps. On permission loss, conceal sensitive details immediately upon detection and invalidate cached grants within five minutes. An outage shows unavailable coverage after grants expire. [Webhook events](https://docs.github.com/en/webhooks/webhook-events-and-payloads#dependabot_alert) · [Failed deliveries](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks)

## Release Review and the local graph

**What shipped.** A published release owns an immutable snapshot of issue IDs, a date and an optional version or GitHub Release URL. Its publish date puts it on the release timeline. A merge, Done transition or date added to the backlog does not establish shipment. Default the publication preview to Done issues in that release. The owner may deselect any of them. Recheck status/revision when confirming and snapshot only eligible selected items. Open, canceled and unselected items stay out of the shipped count. Offer to move open carryover into a new draft as new membership events. Preserve the original release’s historical scope and distinguish a completed, unshipped issue from a published one. Correct an error with a recorded amendment showing who changed what and why. Show separate marks for first shipment and a later release referencing the same issue. In portfolio totals count unique issues by first ship date and separately list release entries.

**What changed.** A release draft has changing membership. Each issue has at most one current draft release per project; selected prior shipment associations are immutable. Moving an issue between drafts records both changes atomically. Freeze the issues in scope at the start of the selected week, and reconstruct subsequent changes from timestamped events. Use the workspace timezone and half-open weekly intervals. Keep an issue counted as open while it is in release scope and in Backlog, Ready or In progress. Done exits as a completion, Canceled or leaving the release exits as removal. A return from Done while in scope is a reopening. Group simultaneous changes into one before/after change in open inventory, and give completion precedence when a previously open item is closed and removed in the same action. Going back to active from Canceled counts as an addition. A published release can retain its historical chart.

| Example release week | Open work after the change | Click to inspect |
|---|---:|---|
| 6 open at the beginning | 6 | Starting issue list |
| 3 added while open | 9 | The added items and why they joined |
| 1 reopened | 10 | The earlier completion and reopening |
| 4 completion events | 6 | All four transitions, including repeat completions |
| 1 removed while open | 5 | The issue and recorded scope change |
| Week closes with 5 open | 5 | Carryover list and next actions |

Render the changes as a waterfall and show the dated shipment markers and manifest separately. A single issue can finish twice, and an issue completed last week can ship this week. An accessible event table reconciles the same totals. Label periods without imported event history “History starts here.” Show raw counts for small projects and an empty state when there is no release yet.

**Obsidian-style graph.** Open one issue’s neighborhood with the issue in the center and explicit edges to the note it came from, blockers and its release. Selecting “decided in” opens the linked section. Selecting “blocked by” opens the blocking issue. Show link type in text, distinguish node types by shape, allow one-hop expansion and provide the same ordered relationships as a list. The public SaaS launch includes this focused view on every plan. Add a whole-project map only after pilots repeatedly need to explore further.

## Markdown portability and migration

Keep raw Markdown as the editable source for notes. Support headings, lists, fenced code, task lists, tags, aliases, common Markdown links and Obsidian-style wikilinks, including heading and explicit block references. Parse links outside code fences and inline code. Persist stable item IDs and the original written targets. For duplicate basenames, prefer explicit paths and offer a chooser for ambiguous references. Preserve unknown frontmatter and plugin syntax as text. Use explicit source paragraph anchors when turning text into an issue. [Obsidian links](https://obsidian.md/help/links) · [Properties](https://obsidian.md/help/properties)

Ship a previewed ZIP import/export. A project export contains `Notes/`, `Issues/`, `Releases/`, original supported images, a versioned `manifest.json` with stable IDs, paths and hashes, and `history.jsonl` for native events and release amendments. An import of the app’s own export can restore the recorded release history after validating and remapping IDs into the destination workspace. An ordinary third-party Markdown or Linear import starts with a current-state baseline. Obsidian note frontmatter uses YAML by convention. Keep it interoperable and preserve unknown fields. App-generated new links use path-qualified targets. Scope the import to the folders the user picks. Skip settings/plugins, including `.obsidian/`. Show unmapped attachments and unresolved links in the preview. Do not ingest arbitrary hidden files. Cap uncompressed bytes and entry counts in addition to tier storage limits.

For a first import, match by source/path and preview duplicates. For a re-import, match stable IDs, compare export-base hashes to current server revisions and incoming hashes, skip identical content, and ask which copy to keep if both changed. Rename by stable ID; a missing file alone never deletes a note. Preserve untouched original bytes on round trip. Test nested images, identical basenames, non-ASCII paths, YAML comments, broken links and two simultaneous edits. Upload the same ZIP twice and require zero new records on the second pass.

For Linear migration, accept the issue CSV for one project, map source statuses and priorities, preview rows and unresolved parents, and import in a transaction. Preserve source ID and original dates, and resolve parent links after all rows exist. Re-import by workspace, import source and source ID. Preserve local edits and distinguish empty cells from deletions. The published export fields and attachment limitations bound the migration. Show users the list of fields brought over and the omitted comments, documents and attachment binaries before confirmation. [Linear export](https://linear.app/docs/exporting-data)

Launch with explicit transfers, bounded uploads and local browser draft recovery after a connection loss. Consider continuous vault sync as a later product decision. It requires persistent device identity, offline revisions, rename tracking, tombstones, conflict recovery and a defined policy for concurrent edits. A separate Rust sync utility keeps product logic in Rust if real usage justifies it.

## Five visual views for one developer

The roadmap is the opening design preview. It puts the current issue and critical security alert above the milestone timeline. Timeline, Burnup and Cycle time each use the full width of the same surface. In the timeline, work names and IDs form a fixed left gutter; the critical archive fix and the storage migration lead into the beta gate. Selecting a milestone opens an inline annotation with its prerequisites. The sample project is Luma. The application is named Ratio, from the Latin ratiō. Its mark is an R with a fraction slash. The reference images use aligned timelines, diamond-shaped milestones, linked panes, a dot per observation and expandable rows. Keep those relationships visible. Use an original high-contrast palette with one accent for selection, distinct risk symbols, direct axis labels and readable grid lines in both themes. A selected mark opens the exact release, issue, source or note behind it. At phone widths, offer an agenda, a compact event list or a unified diff. The standalone [interactive graph examples](ratio-graphs.html) use fictional project data.

| Reference and proposed view | The solo question | Behavior and delivery |
|---|---|---|
| 1 · Cycle-time dot plot | “Why do my maintenance fixes wait longer than features?” | One dot per completed issue. In the grouped view, X is elapsed calendar days and rows are work types. Switch to a time view with finish date on X and elapsed days on Y. Filter by bug, feature, maintenance or security. Measure elapsed time from first In progress to latest Done. **Roadmap semantics.** A prerequisite edge A → B means B depends on A. Reject cycles and highlight the actual chain to the selected milestone. A blocked item names its unresolved predecessor or an explicit external hold. Keep target dates independent of blocker status. Moving a milestone previews affected dependents and requires a deliberate save for each date changed. Sum overlapping scheduled work against optional available sessions or hours only if the owner supplied estimates. A gap on the calendar can represent a break. A dependency chain alone cannot establish a reliable critical path for a developer who can only work on one task at a time.

**Health semantics.** Derive compact text labels with one visible reason. “Needs attention” can mean a missed unfinished milestone, a blocked milestone due within seven days, or an accessible critical security item explicitly tied to that project. When sources are incomplete, show a separate “Coverage incomplete” marker. When there is no target, show “Unscheduled.” A paused project says “Paused” and keeps its security indicator. Show a latest checkpoint date as context. A quiet week alone does not imply poor health.

**Forecast semantics.** Keep the upper burnup line equal to non-canceled issues in the selected release and the lower line equal to the current Done subset. Both can fall. Shipment diamonds use the published manifest date. Count historically observed weekly progress in a comparable project/work-type cohort as Done entries less reopenings, independent of scope moves. Retain zero-output weeks. Exclude the current partial week. Offer the model only after 12 observed complete comparable weeks, at least three positive weeks, positive mean progress and meaningful history coverage. Keep project history boundaries visible. A manually entered future pace is labeled “scenario.”

For a fixed scope, sample whole weeks with replacement, apply signed progress to currently completed work within the scope bounds, and record when all remaining work first reaches Done. Model repeated trials with a reproducible seed. Show the median and 85th-percentile completion week with sample size, assumptions and horizon. The result predicts when work might be ready. Publication is still a separate action. Use the stated availability calendar to skip explicitly planned full weeks off. An unobserved or beyond-horizon result displays a reason in place of a date. Recompute on scope changes and evaluate forecasts against later outcomes before marketing accuracy.

For example, a developer has six items left. In 12 comparable complete weeks their net closures were 0, 2, 1, 3, 1, 0, 2, 1, 2, 1, 0 and 2. Holding scope and availability fixed, the median crosses six by workweek five and the 85th percentile by workweek seven. Mark a vacation in workweek three and those become calendar weeks six and eight. The input's three zero-output weeks stay in the calculation. This is an illustrative model result.

**Cycle-time semantics.** An issue appears once at its latest completion. If reopened, move it to the open-age list until it finishes again. Retain its first start so waiting time stays visible. Exclude unknown starts with a count. Each selected dot opens its issue and timeline. An outlier might reveal that a two-line fix spent 12 days waiting for a certificate. Offer “Open blocker” or “Save next step.” Use counts and named observations with small samples. Protect source-derived details in persisted graphs and shared drill-down endpoints.

Monetize managing more projects and understanding a longer release history. Release the planned cycle-time dots and on-demand PR diff to all plans within each plan’s connected repositories and visible date range. ## Data model and runtime

| Records | Invariant |
|---|---|
| User, workspace, session, project | One private workspace per account and one owner per workspace. Every content query derives its workspace from the authenticated session. Project keys are unique inside that workspace. |
| Item, issue, note, revision | A stable item ID survives title, path and project-name changes. Issue keys are human-readable. Notes retain raw Markdown. An expected revision on edits prevents one browser tab overwriting another. |
| Checkpoint | Store the issue, optional note anchor, next action and saved time per project. Owner activity timestamps advance only on meaningful user actions. |
| Edge | Store typed, directional relationships between same-workspace items. Authored blocking relationships and parsed wiki references have separate origins. Rebuild parsed edges in the revision transaction. Index source and target so graph and backlinks use the same records. |
| Milestone, dependency, release, manifest entry | A milestone has an optional target and explicit predecessors. Scheduled spans are user-entered. Reject dependency cycles. Store a versioned release manifest separately from editable issue state. |
| Issue event, scope membership | A status or membership change and its immutable event commit together. Stable IDs make retries idempotent. Keep event time, ingest time, source and grouping for simultaneous changes. A current-state projection serves the board. |
| Source connection, repository grant, source alert, work link | Keep upstream severity and state separate from local work. Cache only fields needed by authorized views. Use a unique repository-source identity and alert number inside each workspace. |
| Import run, job, subscription, entitlement | A unique source key per imported item prevents reimport duplicates. Lease jobs and deduplicate billing deliveries. Apply plan limits on the server and inside the transaction that creates the resource. |

Use compact workspace-scoped HTTP endpoints for Home, issue changes, checkpoint saves, note revisions, graph neighbors, Review events, imports/exports and billing. Gate each in a single authorization layer backed by tenant-scoped SQL. A source-derived field needs an additional current source grant. Use foreign keys that include workspace ID. Use a non-owner DB role and integration tests with two workspaces. Test deep links, searches, counts and exports as well as direct record reads. Index workspace/project/status/update time, event timestamps and both sides of links. Start with PostgreSQL full-text search on user-owned titles and bodies. Bind dynamic source details at read time.

## Deploy and operate on Railway

Use one stateless application service, one private PostgreSQL service in the same region, and private object storage for attachments. Back up attachments separately, retain versioned objects off-account, and verify their hashes against the restored database during a drill. The web process leases short background jobs from PostgreSQL with bounded concurrency, retries and visibility timeouts. A separate worker can use the same binary and database when queue delay competes with request latency. Serve fingerprinted assets with immutable cache headers. Keep account pages private and user-specific. Choose the production region nearest the initial customer cohort and record it on the privacy page. Use a separate staging environment and synthetic data. [Railway private networking](https://docs.railway.com/networking/private-networking/how-it-works) · [Regions](https://docs.railway.com/deployments/regions)

Build a multi-stage Docker image with a pinned Rust toolchain, locked crates and a non-root runtime. CI runs formatting, linting, domain and SQL integration tests, a browser journey and a release build. Deploy the tested image. Bind to all interfaces on the injected `PORT`. Run additive SQLx migrations under a single lock in the pre-deploy step. Return 200 from `/readyz` only when the schema and database are ready. Keep the old app compatible with the new schema until the rollout is stable. Roll a bad image back immediately. Repair a data migration forward or restore separately. ## Trust and data ownership

Choose email one-time sign-in with a verified transactional sender, short-lived single-use tokens stored hashed, session rotation and an authenticated account-recovery flow. Independently connect GitHub after sign-in. Use secure HttpOnly cookies, CSRF protection, session expiry and rate limits. Record important operations without capturing free-text content. Keep private project images in a private object bucket with short-lived downloads, bytes and digests verified on upload. Downloads, full-text search, graph edges, chart drill-down and exports share the same authorization layer.

Keep native notes and issues private to their owner. References to imported alert details resolve dynamically. Limit access to the intersection of workspace access and the viewer’s current GitHub rights. Permission loss removes the private association from the alert card, issue preview, search suggestions, health totals, graph edges, digest and old hosted export links. Recheck grants before generating/downloading a source-inclusive export. Use a native-content-only export by default, with an explicit option to include eligible source metadata. Store operator keys and refresh tokens encrypted, with rotation and revocation procedures.

Disconnecting a repository stops queued work and invalidates downloads and cached views immediately. Purge its imported metadata within 24 hours. Keep standalone user-authored work. For a plan-limited paused connection, stop sync, label coverage paused and suppress security details unless a fresh check proves access. A downloaded copy remains under its recipient’s control.

Account deletion immediately revokes sessions and disconnects integrations. Complete primary database and attachment deletion within seven days, expire independent encrypted backups after 30 days, and use a deletion ledger outside the restore snapshot to reapply deletions before serving recovered data. Publish actual backup retention, the distinct lifecycle of provider-held billing records and the support contact before launch. Keep only necessary billing identifiers in the tracker. Use Railway PITR and independent 30-day backups for production. Verify any additional snapshot retention and disclose its actual expiry in the policy before enabling it.

**Launch channel.** Recruit ten pilot developers across solo products, weekend projects and freelancers through existing developer communities and individual opt-in invitations. Ask each to show a project they actually paused. Observe them finding their next action in their current tool, then in this tracker across a comparable interruption. Put a sample project plus a short screen recording of that specific workflow on the landing page. Publish a guide to importing one Linear project and one Markdown folder. Offer guided migration to the initial pilot; turn repeated steps into onboarding.

**Measures.** Activation means a real project, a linked issue and a saved checkpoint within seven days. Measure successful resumption when a returning user opens that checkpoint after at least a day and records a meaningful action. Record median time to resume in observed sessions; opening Home is insufficient. Measure the weekly count using a real chart drill-down, four-week retained workspaces, paid conversion by plan, first renewal, infrastructure cost, support minutes and cloud-model spend when available. Use opaque IDs, timestamps and counts with a clear product-analytics choice. Keep notes, alerts and repository identities out of analytics.

**Early decision rule.** In an initial cohort of ten, aim for six activations, four voluntary returns on separate weeks and three customers who renew once. With a small cohort, interview the people behind each count. Offer Max to developers who already compile several projects’ release notes. Seek at least two real purchases tied to its portfolio review before expanding that tier. If people like a chart but never use it to find an issue or make a release decision, improve that path before building another chart.

**Protect the first release.** Prioritize the Home resume/security loop, trustworthy release history, the personal roadmap and portable notes if estimates grow. A link to GitHub can carry the code-review workflow until the inline diff is ready. Manual availability and a visibly labeled pace scenario keep the roadmap useful while a new workspace accumulates history. Native clients, collaboration roles, full two-way vault sync, custom workflow engines and general-purpose AI agents are separate future decisions.
