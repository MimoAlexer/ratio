# Engineering implementation plan

Build the first paid release of a private issue tracker for solo developers. A returning developer should be able to resume an issue, act on a critical security finding and verify what shipped. Use the [product plan](product-plan.md) for the customer journey and pricing rationale. The paths below describe a proposed new repository.

## Delivery budget

Plan for one developer working 25 focused hours a week. The central estimate is **500 hours over 20 weeks**, including pilot feedback and launch qualification. The planning range is **400–550 hours over 16–22 weeks**. The low end assumes the first integration and import fixtures pass with little rework. Re-estimate after the private alpha and beta. Keep paid checkout in test mode until recovery and access controls pass.

| Weeks | Hours | Deliverable | Depends on |
|---|---:|---|---|
| 1 | 25 | Walking skeleton and early integration checks | — |
| 2–4 | 75 | Private tracker, event history and Home checkpoint | Foundation |
| 5–6 | 50 | Linked notes, local graph and paragraph-to-issue | Tracker |
| 7–8 | 50 | Milestones, health, manual flags, basic export and private alpha | Issues and links |
| 9–11 | 75 | Read-only GitHub, critical alerts, PR context and diff link | Identity, issues, grants |
| 12–14 | 75 | Release Review, observed burnup, Markdown import and beta | Event history and milestones |
| 15–16 | 50 | Markdown round trip, image storage and Linear migration | Revisions, releases and links |
| 17–18 | 50 | Billing, paid features and entitlement transitions | Storage and history queries |
| 19–20 | 50 | Restore drill, performance and accessibility qualification, paid launch | All previous slices |

## Repository and interface boundaries

| Proposed path | Responsibility |
|---|---|
| `crates/core/src/` | Pure Rust rules for issue transitions, checkpoints, release math and versioned plan entitlements. |
| `crates/server/src/` | Axum routes, authenticated application services, SQLx queries, provider adapters and a bounded PostgreSQL job runner. |
| `crates/web/src/` | Leptos server-rendered pages and selectively hydrated Rust controls. Render the graph on demand. Use a standard HTML form for core writes. |
| `migrations/` | PostgreSQL records, same-workspace foreign keys, unique command/delivery keys, indexes and replayable event history. |
| `xtask/src/main.rs`, `crates/server/tests/` | Rust build and qualification commands, provider fixtures, integration tests and staged browser journeys. |
| `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `Dockerfile`, `.railway/railway.ts` | Native Rust project settings, pinned builds, non-root runtime image and Git-reviewed Railway infrastructure. Use typed Rust defaults, runtime environment variables for secrets, JSON on provider APIs and in the portable manifest. Manage provider-only settings in the dashboard. [Railway IaC](https://docs.railway.com/infrastructure-as-code) |

`WorkspaceAccess` comes from the server session. A client-supplied project or item ID is only a lookup key inside that scope. `RepoAccess` also requires a current GitHub user grant for the requested capability. Use both scopes for source-derived fields on every read. Authorize before serving cached data or constructing downloadable content. Store user-authored material separately from upstream fields so removing a connection preserves the developer’s work.

## Implementation backlog

### 1. Deploy the smallest usable slice · week 1

- [ ] Create the workspace, staging Railway environment, private PostgreSQL, secrets and same-region app. Review the Railway IaC plan against staging. Build the pinned multi-stage image, bind the server to the injected `PORT`, and run additive SQLx migrations under one lock in pre-deploy. Put schema/DB checks in `/readyz`. Record dashboard-only settings in `ops/railway.md`. [Railway pre-deploy](https://docs.railway.com/deployments/pre-deploy-command)
- [ ] Serve a Leptos Home fixture with an ordinary form from `crates/web/src/home.rs`. Load an interactive 100-node sample graph on its own route. Measure the first visit on a mid-range laptop and throttled mobile. Record transfer size, input delay and failure behavior when browser hydration is unavailable.
- [ ] Reserve eight hours across weeks 1–2 for two feasibility checks. Use a controlled private repository and two GitHub accounts with deliberately different alert access. Verify installation binding, user-token access and hiding an alert after revocation while PR access remains. With a small permissioned vault fixture, parse a renamed note, duplicate basename, fenced wiki link, heading and original frontmatter. Record unsupported cases and adjust the later GitHub/transfer estimates at the end of week 2.
- [ ] Gate the milestone on deploying one tested image, migrating an empty database, successfully submitting the form and rolling back to the preceding schema-compatible image. Give CI one entry point, `cargo run -p xtask -- verify`, for formatting, Clippy, tests and a release build.

### 2. Make an issue resumable · weeks 2–4

- [ ] In `crates/server/src/session.rs` and `migrations/0001_workspace.sql`, implement private sign-in, secure revocable sessions, CSRF protection, a single owner per workspace and tenant-scoped project keys. A session that expires mid-edit should return the developer to the intended issue after sign-in.
- [ ] Add `issue.rs`, `checkpoint.rs` and the issue/revision/event tables. Every mutation carries a command ID and expected revision. Return the previous result for a repeated command and a visible conflict for a stale revision. Commit old/new status and scope, event ID, group, effective time, ingest time and actor in the same transaction as current state. Include work type and milestone IDs for later views.
- [ ] Implement list/board/search with PostgreSQL full-text indexes, issue keys, blockers, labels, archiving, undo via a compensating event and keyboard-accessible status changes. Select the latest explicit checkpoint on an open issue, then the most recent developer-edited in-progress issue, then an onboarding action. Exclude sample data from real reports.
- [ ] Gate in `crates/server/tests/resume.rs`. With two accounts, direct reads, search/counts and mutations stay within their workspace. Closing or archiving the top checkpoint reveals the next eligible item. A passive visit or webhook preserves the order. Repeated submissions make one event. Concurrent edits preserve both parties’ ability to recover their work.

### 3. Recover the decision behind an issue · weeks 5–6

- [ ] In `crates/core/src/links.rs`, parse Markdown and wiki references outside code, including paths, headings, aliases and explicit block IDs. Preserve raw Markdown, unknown frontmatter and original targets. In `crates/server/src/notes.rs`, save the revision and rebuild its derived links in one transaction. Index both ends of each typed edge.
- [ ] In `crates/web/src/note.rs`, create an issue from a selected paragraph and retain a stable source anchor and excerpt. Add backlinks, safe preview, source-labeled edges, a one-hop graph, keyboard navigation and an equivalent relationship list. Protect pending browser drafts across interruptions and scope them to the signed-in account.
- [ ] Gate on duplicate note names requiring a choice, note rename preserving links, changed anchors offering the retained excerpt, and a concurrent revision conflict preserving edits. Rehearse the first five minutes from an empty account through note → issue → next action. The first Home response must contain the resume action with the graph bundle unloaded.

### 4. Show dependencies, project health and manual findings · weeks 7–8

- [ ] Build `crates/web/src/roadmap.rs` for release and milestone spans, planned targets, actual shipment markers and unavailable weeks. Add a detail editor and mobile agenda. An arrow from A to B means B depends on A. Reject cycles transactionally, preview downstream impacts, and require deliberate saves for changed dates. Use workspace-local calendar dates and an equivalent dependency list.
- [ ] Add `crates/core/src/health.rs` and `crates/web/src/portfolio.rs`. Expand project → release → milestone → blocking issue, hiding empty levels. Show “Needs attention” with a contributing issue for an overdue unfinished target, a blocked milestone due within seven days or an accessible critical tied to the project. Treat incomplete coverage, paused projects and unscheduled work explicitly. Ship per-project health on Free and the cross-project rollup on Max. Show critical findings beside active work on Home. Manual flags have a severity, a next action and a local close/reopen operation.
- [ ] **Private alpha.** Provide a native Markdown download of the pilot’s issues, checkpoints and raw notes, and read it in a plain editor. Enable database recovery and an encrypted independent backup before onboarding a pilot’s real project. Ask a returning pilot to find yesterday’s next step, follow a dependency to its blocker and open a manual critical finding. Record time, errors and any manual explanation required. Test date edits, keyboard-only navigation, narrow layouts and a critical finding arriving alongside an existing checkpoint. Reserve GitHub coverage in the UI for repositories with a successful check.

### 5. Connect GitHub with least privilege · weeks 9–11

- [ ] Implement `crates/server/src/github/{grants,pull_requests,alerts,jobs}.rs`. Bind an installation to a workspace after verifying the signed-in GitHub user and selected repos. Map each active repository to one project per workspace, allowing several repositories per project. Enforce the mapping with a workspace/repository uniqueness constraint. Request read access for PRs, Dependabot alerts and required metadata. Keep sign-in independent of the installation. Verify the user’s effective authority independently for PR and alert reads. [GitHub Dependabot API](https://docs.github.com/en/rest/dependabot/alerts#list-dependabot-alerts-for-a-repository)
- [ ] Link a PR by pasted GitHub URL or explicit issue key. Prompt on ambiguity. Show PR number, title, state and a working link to GitHub’s **Files changed** view. Render source details through a fresh grant. A merge leaves local status and shipment under the developer’s control.
- [ ] Page the initial seed. Verify signed webhooks, deduplicate delivery IDs, lease jobs and re-read current upstream state when events arrive out of order. Reconcile hourly with jitter, rate-limit refresh and track coverage per repo. Report zero only after a complete successful sweep. After two missed sweeps mark coverage stale. Show checked/unavailable counts separately.
- [ ] Store upstream findings by workspace, stable repository ID and alert number. `start_fix(access, finding_id, command_id)` returns one existing or new issue even on concurrent clicks. Create new fixes in the mapped project. Moving a repository or its linked issue preserves the workspace-level finding identity and the existing fix link. Show open upstream criticals and manual criticals with distinct provenance. Completion of local work preserves a still-open finding. Upstream reopen reuses the original fix link.
- [ ] Gate in `crates/server/tests/github_access.rs`. Exercise a public repo with private alerts, lost alert permission while PR permission remains, removed repository, uninstall, failed second page, duplicate delivery and expired user grant during provider outage. Known revocation conceals data immediately, and grant cache lifetime is at most five minutes. Recheck Home counts, deep links, search, graph, exported files and digest links. On disconnect, stop jobs, invalidate grants and purge stored source details on the published retention schedule. User-authored notes and fixes remain accessible.

### 6. Reconcile a release to its issues · weeks 12–14

- [ ] Introduce `crates/core/src/review.rs` and `crates/web/src/release.rs`. Preselect the current Done issues in the release. Let the developer narrow the list, then revalidate scope, status and revision transactionally at confirmation. Publish an immutable snapshot of the selected Done IDs, date and optional version/URL. Open and canceled work stays unshipped. Offer an explicit action to move selected carryover to the next draft, recording new membership events and retaining historical scope. Amend with a new recorded entry and reason. Distinguish first shipment from a later release entry. Portfolio totals count each issue at its first shipment. Publishing twice with the same command returns the same release.
- [ ] Define `review_week(events, release_id, local_week) -> ReleaseWeek` and replay effective event groups in a deterministic order. Use half-open workspace-local weeks, including daylight-saving transitions. Count open issues in scope with statuses Backlog, Ready or In progress. For one atomic edit compare before/after state once. Completion takes precedence over simultaneous removal. Returning from Done while in scope is a reopening. Returning from Canceled adds open work. Imported current state establishes a visible history boundary.
- [ ] Draw an observed burnup with dated scope and completed counts, a scope-change waterfall and dated shipment markers. For each day the scope count is the non-canceled issues assigned to the release and completed is its Done subset. Reopening or scope removal can lower a line. Every chart mark has a drill-through to the precise issue set or event group and an equivalent labeled table.
- [ ] **Beta.** Offer a selected-folder, Markdown-only import with byte/entry limits, hidden-path exclusion, duplicate preview and an atomic commit. Gate on a repeated import creating zero notes and show unsupported attachments before confirmation. `crates/server/tests/release_review.rs` must reconcile **6 starting + 3 added + 1 reopened − 4 completed − 1 removed = 5 carried**. Cover repeated completion, Done and removal in one command, completion before the week then shipment inside it, one selected Done issue reopened between preview and publish, carryover moved after publication, amendment, two release references and a week with partial imported history. Have a pilot explain the five carried issues and identify the actual shipped list from the same release.

### 7. Move real project data in and out · weeks 15–16

- [ ] In `crates/server/src/transfer/{archive,linear,blobs}.rs`, preview a selected-folder Markdown ZIP and one-project Linear CSV. Show incoming fields, ambiguous paths, unsupported entries and proposed changes. Preserve original bytes of untouched notes and supported images. Export `Notes/`, `Issues/`, `Releases/`, images and a versioned `manifest.json` with stable IDs, paths and base hashes. Put native events and release amendments in `history.jsonl` and support validated, ID-remapped restoration on every tier.
- [ ] Stage immutable image objects privately before committing references. Include object versions and their checksums in the independent backup before accepting pilot uploads. Validate paths, decoded byte count, entry count, type and quotas before promotion. Sweep abandoned uploads. Use scoped downloads. Match first imports by source/path or Linear source ID, then use stable IDs and base/current/incoming hashes. Handle rename, identical data and two-sided edits explicitly. Missing input alone leaves existing records intact. Resolve Linear parents in a second pass inside the import transaction.
- [ ] Gate on a second identical import creating zero rows, concurrent uploads respecting quota, an interrupted import exposing no partial project, and an export/import/export round trip retaining links, dates, unknown YAML and image hashes. Include nested images, duplicate basenames, non-ASCII paths, oversized archives, symlinks and entries outside selected roots.

### 8. Charge for the advertised three tiers · weeks 17–18

- [ ] Define versioned `PlanLimits` in `crates/core/src/entitlements.rs`. Apply limits in the same transaction as each resource creation, import or upload reservation. Preserve native data and full exports at every tier. Alert freshness is identical for each actively connected repo. Cap individual note source at 2 MB and run quota checks against uncompressed stored bytes. The meter includes user content and retained uploads, with an explicit release date for soft-deleted blobs.

| Monthly account plan | Active projects / repos | Storage / image cap | Release review | Paid workflow |
|---|---|---|---|---|
| Free · $0 | 1 / 1 | 100 MB / 5 MB | Latest 30 days, project | Built-in views |
| Plus · $5 | 10 / 10 | 1 GB / 10 MB | Latest 12 months, project | Personal saved views and templates |
| Max · $15 | 50 / 50 | 5 GB / 20 MB | All recorded history, cross-project | Cross-project saved views and scheduled private portfolio digest |

- [ ] Implement `crates/server/src/billing.rs` using hosted checkout/portal, verified webhooks, current provider subscription state and nightly reconciliation. Display proration and renewal date before checkout. Model pending checkout, paid, scheduled downgrade/cancel, past-due grace and Free. Grant paid features after payment confirmation. At renewal allow the owner to choose active projects/repos. A failed payment starts the proposed seven-day grace period. On expiry apply Free and retain read/export access to excess projects. Pause excess syncs and ineligible digest schedules. Keep source permissions in force for historical views.
- [ ] Gate in `crates/server/tests/entitlements.rs` with duplicate/reordered callbacks, abandoned checkout, simultaneous creations of the last slot, failed payment with recovery, grace expiry, downgrade and re-upgrade. Verify reducing edits/deletions still work at the cap, a previously scheduled email opens a newly authorized private view, and full export includes native history beyond the paid chart window. Complete a test customer’s full checkout-to-cancellation journey and confirm plan views, templates and digest behavior on each tier.

### 9. Qualify the paid launch · weeks 19–20

- [ ] **Recovery.** Verify database point-in-time recovery and private object versioning. Produce a nightly encrypted off-account copy of the DB and referenced blob versions with a timestamped manifest and checksums. Retain versions through the database restore window. Restore to an isolated DB and bucket, verify every referenced blob exists, sample content checksums and rebuild a release chart. Replay a separately retained minimal deletion ledger, invalidate restored sessions and provider credentials, and rehearse staged cutover. Target ≤15 minutes of database loss and ≤4 hours recovery from primary DB failure while blob storage remains healthy. Target ≤24 hours of data loss for whole-project recovery from the independent copy. Time both paths, including file retrieval, before promising an objective. Repeat the drill monthly.
- [ ] **Load and accessibility.** Seed 10,000 issues, 2,000 notes and 50,000 links. At 25 concurrent same-region users target warm server p95 ≤150 ms for Home/list/detail and ≤250 ms for search. Record query counts and errors. Target p75 LCP ≤2.5 s and INP ≤200 ms in real use, with initial lab runs clearly labeled. Open a warmed graph of 100 nodes and 250 edges within one second on a recorded device. Exercise focus order, zoom at 200%, screen reader, reduced motion, mobile touch and hydration loss.
- [ ] **Operations.** Test external uptime and alerts for 5xx, DB pool waits, oldest queued job, per-repo check age and backup age. Inspect telemetry for credentials and personal content. Rehearse revoke, account delete and recovery. Verify account-scoped draft cleanup, grant expiry on old links and fresh authorization after restore. Record the tested image, migration, test reports, restore times and unresolved pilot issues in `ops/launch.md`. Verify merchant region, fees/tax setup, pricing, support and privacy disclosures before enabling live checkout.

The two assistant stages run in order and can be scheduled independently of the analytics updates. The paid-launch budget covers stages 1–9. Estimate post-launch work separately once the pilot provides representative histories, diff sizes and a target assistant client.
