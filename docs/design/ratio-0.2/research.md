# Reference study for Ratio

Reviewed November 20, 2026, before implementation. This study uses official product documentation, five product screenshots and the public design articles. The Linear images are documentation examples. Keyboard behavior is taken from the documentation, as I did not sign in to a Linear workspace.

## What the sources show

- Linear’s March 2026 refresh reduced the contrast of inactive navigation, trimmed icon treatments and removed separators that lacked a clear job. The team reviewed changes in the running product and tuned its default dark palette toward a less saturated gray. The reason for the header work was that similar actions had migrated to different places on different screens. [A calmer interface for a product in motion](https://linear.app/now/behind-the-latest-design-refresh)
- In 2024, Linear treated the sidebar and header as connected global navigation. Its designers compared list, board, reading and split views with browser and desktop chrome, including window actions that only exist in the desktop app. They checked the vertical and horizontal alignment of labels, icons and buttons and tested how the same colors worked across surfaces. [How we redesigned the Linear UI](https://linear.app/now/how-we-redesigned-the-linear-ui)
- The case for a system-wide redesign was accumulated design debt. Individually reasonable additions had changed how the surfaces worked together. The argument is particularly pertinent to a product in which people move between an issue, a note and a release in one session. [A design reset](https://linear.app/now/a-design-reset)
- The public Refactoring UI example demonstrates how spacing and different surface tones can separate groups where a succession of outlines adds noise. Its published contents also call attention to baseline alignment, line length and balancing text weight against contrast. Only the public material was reviewed. [Refactoring UI](https://refactoringui.com/)
- Vercel’s guidelines recommend preserving browser zoom, expanding compact targets, making focus visible and returning it when a dialog closes. They also cover long content, sparse and dense views, actionable recovery, redundant status cues, reduced motion and loading feedback that retains the action label. These are useful criteria for the browser app and its desktop webviews. [Web Interface Guidelines](https://vercel.com/design/guidelines)

## Decisions suggested by the Ratio baseline

Reviewed the existing Linux desktop issue-list and issue-detail images in the repository, and the freshly captured 1440 × 900 Home, Issues, Projects and Settings pages.

1. **Lead with the work to resume.** The Home title, checkpoint title and New issue/Resume issue actions have similar visual prominence. Make the saved checkpoint and next action the focal point when present, with its actual project and timestamp alongside. Keep an actionable first-run Home for a workspace with no checkpoint.
2. **Give the issue title more of the row.** At 1440 px, ID occupies a broad leading column, with Type, Priority and Updated spread across the opposite edge. Keep readable IDs, compact comparative fields and leave long issue titles a continuous reading lane. When several projects are in scope, project identity must remain legible. A status group already supplies status for its rows.
3. **Set the chrome to one rhythm.** Ratio currently repeats navigation context in the sidebar, 54 px header and large page title. Assign each a job and share edges. Keep global navigation, search and current-page actions predictable. The Ratio mark, existing font pairing and matched native frame give sufficient identity.
4. **Use boundaries selectively.** Ratio already avoids card grids. Soften repetitive horizontal rules inside dense lists, and preserve stronger distinctions at actual changes of group or surface. Distinguish hover, keyboard focus, selected navigation and critical findings using both shape and luminance. The danger state and priority must remain intelligible in the monochrome theme.
5. **Keep detail views readable at both scales.** The existing property rail and Next action are useful. Give the checkpoint a direct visual relationship to the issue’s description. Preserve access to history and blockers and prevent sparse metadata or empty sections from overtaking the reading column. Keep edit and status controls reachable on narrow screens.
6. **Maintain server-rendered interaction semantics.** Core Ratio workflows already use links and forms with JavaScript disabled. Reuse those controls for styling and progressive keyboard enhancement. Check escape, target size, focus restoration, link destinations and visible validation at desktop and phone widths.
7. **Make empty/error states specific.** An empty workspace, a filter with no matches, a project limit and an unavailable GitHub connection have different next actions. Outline the relevant action in place. Leave meaningful sparse screens sparse, and reserve loading feedback for real pending operations.
8. **Review the whole workflow in context.** Use the same seeded issue and project to compare list, detail, note, project and roadmap at a common zoom. Test long content, selected controls, a failed form, phone and keyboard navigation, both appearance settings, and native webview rendering when available. Keep evidence of defects and fixes in successive captures.
